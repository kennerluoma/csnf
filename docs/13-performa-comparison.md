# 13 · Performa 2025: the agent's PR vs the production site

Second real design (2026-09-17): `examples/performa-2025.fig` (Finals page, 7 frames) → [performa-2025#1](https://github.com/kennerluoma/performa-2025/pull/1), 30 min, $16.30, no renders, one plan pass + one implementation pass. Compared with the shipped site (`examples/performa-2025-site`, Next 15 app router, static export on Netlify, Sanity v4, 121 TS files, 390 commits 2025-07 → 2026-03).

The site is much larger than the design: 12 route groups, 5 document types, 3 singletons, ticketing, search, a password-protected press area, a studio sub-programme. The design shows four screens. So this comparison is less "what did the agent miss" and more "what does a festival site need that no design ever draws".

## What the agent matched

- The split header (coloured left, white right), the per-screen background colour, the "RADICAL BROADCAST" dismissable item, the livestream bar as site chrome (production: `MarqueeLivestream`, a fixed bottom bar with a marquee and a live/next broadcast, driven by the same event data).
- Calendar as a date-grouped list with filters in the URL. Production: `SortAndFilter` with Timeframe / Type / Programming written to the query string via `nuqs`, filtering client-side over the full prerendered event list (`useEventFiltering`).
- Events as the core type, with artists, tags/series, images, a schedule with ticket state. Production's `event` has exactly that shape: `types`, `tags`, `artist`, `mainImage` + `images` (each with caption and rich caption), `video`, `livestreamUrl`, `schedule[]` (date, time, duration, ticketId, label), `venue` (a document), `credits` with logos.
- Lightbox with counter, caption toggle, prev/next, close. Production: `Lightbox` on Splide, with a video slide type and auto-hiding controls.
- Mobile: stacked columns, overlay menu. Production: `ExpandedMenu` from a valtio UI store, with menu/search mutual exclusion and sequenced animations.

## What the agent did that production doesn't

- Filters are server-resolved (URL params → resolver → list), so filtered URLs are shareable and render without JS. Production filters client-side over the whole list, which is fine for 13 events and would not be for 300. Both are valid; ours degrades better.
- Broadcast as a route (`/broadcast`) instead of a state colour. Production has `/broadcasts` and `/broadcasts/[slug]`, so the agent's reading of "Red Alt" was right.

## Design drift

Same pattern as Alex Olson, stronger: the design is four screens and the site is twelve route groups. Ticketing, search, press kit, studio events and the venue model were all decided in code. The first build cannot know them; the issues queue is where they arrive, and most of them are client-specific enough that the right response is a fix session, not a template rule.

## What changed because of this

- Template: prerender, ISR, router links, config-only image builder (performance); `event.venue` reference; live-state helpers. Search box and menu groups are queued as template work, not done.
- Lessons candidates for `agency learn` (needs a second project to confirm): festival/venue sites need a venue document; an email field in a menu is a newsletter signup; "search" icons in a design imply a search route.
